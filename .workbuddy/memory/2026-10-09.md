### ⭐⭐ 官方对首/尾帧的处理方式不同（这个细节很关键）
```python
if first_frame is not None:
    img = _resize(first_frame[:1], width, height, "disabled")   # 首帧：几何锚
    keyframes.append({"resolved_frame_index": 0, "image": img})
if last_frame is not None:
    img = _resize(last_frame[:1], width, height, "center")      # 尾帧：跟随者
    keyframes.append({"resolved_frame_index": frame_count - 1, "image": img})
```
- **首帧 = 几何锚**（`"disabled"` = 直接拉伸到画布，不裁切）→ **构图/机位/透视由它定死**
- **尾帧 = 跟随者**（`"center"` = 等比cover-crop）→ 只锁末帧内容，不锁构图

→ **实用推论：想让整段构图稳定，首帧参考比尾帧参考更强。**
  只给尾帧时，模型仍可能自由重构整个镜头。

### ⭐ 我们现有的 chain 工作流用的就是官方节点（不用改）
查 `xs001_segs/_last_api.json` 实测：
```

911  MiniMaxH3AddGuide            frame_idx = 0        ← 把上一段尾帧锚在本段第 0 帧
910  VHS_LoadVideoPath            video=off_xs01_t03_00010-audio.mp4
                                  skip_first_frames = 221, frame_load_cap = 22
```
所以「续写链」的实现方式 = **官方 `MiniMaxH3AddGuide` 在第 0 帧打尾帧锚**，
不是我自创的偏方。**它属于 fl2va 模式，官方支持。**

### ⚠️ 但我们的用法只用了官方能力的一半
官方 `MiniMaxH3AddGuide` 支持的能力我们**全都没用上**：
1. ⛔ **`frame_idx` 恒为 0** —— 只在开头打锚，从没在中间或结尾打过
2. ⛔ **没同时给 `first_frame`** —— 没锁构图，只锁了上一段尾帧的内容
3. ⛔ **没用 `audio` 输入** —— 上一段的**音轨没接过来**（声音不连续）
4. ⛔ **没链多个 AddGuide** —— 官方明确说「Chain several nodes to anchor several frames」

## ⛔⛔⛔ 13:35 连跑入口也有 prev 漏洞（硬校验救了一次）

跑 `_chain.py 3 4 5 6 7 8` →22 秒就停，日志只到 `[1/6] seg03`：
```

[13:32:30] !!⛔⛔ 本该 chain 却退回 fixed：上一段尾帧没找到
```
**根因**：`prev` 只在两种情况有值——①单段入口 `find_prev_video` ②**上一段刚跑完**
（循环末尾 `prev = got`）。连跑多段时，**第一段**如果自己不是链组开头（3 不是），

症状极具迷惑性：**只跑 22 秒、日志像"跑不动了"**，实际是守卫正确拦住了静默降级。
（若没那道守卫，就会安静地出一段 fixed 的 seg03，看着成功、实际没接上。）

**修法**：循环内 `last_group` 赋值之后加：
```python
if prev is None and kind_of(sid) == "chain":
    prev = find_prev_video(sid)
    log("  ↳ 接上一段（%d）: %s" % (sid-1, os.path.basename(prev) if prev else "（找不到）"))
```
✅ 实测 `find_prev_video(3)` → `off_xs01_t02_00014-audio.mp4`（刚认可的那支），
`job03_chain.json` 对账：workflow=chain / prev=t02_00014 / refs=4。

### ⛔ 由此可推广的判断
**「守卫正确报错」和「功能坏了」要分开看。** SystemExit(6) 是那道硬校验在起作用
（不许 chain 静默退回 fixed），它保护了我；但它同时暴露了「连跑入口没接 prev」的功能洞。

## 15:46 ⛔⛔⛔ 看板能看视频吗？—— 不能。自动刷新把播放器每 3 秒重建一次

**用户原话（我第三轮被骂，这次骂得对）**：
> 「你这网页 每几秒刷新一下 我怎么预览视频啊？？？？你他妈做事没脑子的吗」

**现象**：网页每 3 秒 `load()` → `render()` → 重建整个预览区 `<video src=...>`。
浏览器**重新加载 video 元素** → 进度归零、声音断、正在看的那一帧被抽走。
结果：一支 10 秒的片**一帧都看不了**，用户被迫反复从头点。

**⛔ 根因不是「刷新太频繁」，是「刷新时碰了 `<video>` 元素」。**
频率只是放大器；哪怕 30 秒刷一次，看第 8 秒时照样被重置。

**三条修法（已实测验证）**：
1. ⛔ **同一支片绝不碰 `<video>`**：`lastVsrc` 记住 src（含 `?v=<mtime>`），
   `if (vsrc !== lastVsrc)` 才重建。src 相同 = 刷新时**一个像素都不动播放器**。
   → node 模拟：连刷 5 次 → 重建 **1** 次；切片 → 2 次；新成片落盘(ts 变) → 3 次。✅
2. ⛔ **用户一碰播放器就自动停刷新**：监听 `play` / `seeking` / 播放器上 `pointerdown`（捕获阶段）→
   `autoPause()` → `clearInterval`。
   **这条比「暂停按钮」重要**：人一定先点播放，不会先找按钮。
3. 给显式「暂停刷新 / 继续刷新」按钮，让用户知道状态（顶栏 `看片中 · 刷新已停`）。
4. 指令（reject/resume）后**立即** `load()` 一次拿反馈，但 render 不碰播放器。

**→ 落进 skill 的通用判据**：
> **任何带自动刷新的页面，凡是有 `<video>` / `<audio>` / canvas / 地图 / 正在编辑的输入框，
> 刷新时就绝不能重建那个元素。** 刷新只改「数字和状态」，不改「用户正在看的东西」。
> 同理：**不要在用户输入的 textarea 旁边做整块 innerHTML 重绘**（会把没提交的输入冲掉）。

**次要修正**：预览按钮文案改成动态（`否定片N · 整条链M重排`），
让用户点之前就知道会连带哪几片。
