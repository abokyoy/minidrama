## 踩坑

### ① 工作流 JSON 是 **UI 格式**不是 API 格式
`j['nodes']` 是 list，节点有 `type` / `widgets_values`，**没有 `class_type`**。
按 API 格式解析会`AttributeError: 'str' object has no attribute 'get'`。
官方蓝图更绕：节点在 `j['definitions']['subgraphs'][0]['nodes']`。

### ② Python的 `urllib` 走不了代理（WinError 10061），curl 可以
同一台机器、同一代理，curl 正常、urllib 直接拒连。
→ **下载一律用 bash + curl，不要用 Python 写下载器**（`_dl_hf.py` 已废弃）。

### ③ `nohup ... &` 之后父 shell 退出 → 子 curl 全被带走
分片停在半路，前功尽弃。
→ **整条下载命令必须作为后台任务的主进程**（`run_in_background=true` + 直接跑脚本）。

### ④ curl 两种写法在本机的行为不同
- `curl -o /path/file` → **写不出文件**（0 字节 / exit 7）
- `curl ... > /path/file`（重定向）→ **正常**
→ 脚本里一律用 `>>` 重定向追加。

### ⑤ `curl -C -` 不能和 `-r` 一起用
两个都改Range，会下错偏移。
→ 手动算：先 `stat` 看本地已有多少，把 `-r` 起点往后挪（见 `_dl_h3_models.sh` 的while 循环）。

### ⑥ PowerShell 工具 stdout 被吞 + 中文路径 cmd 被 mangle
→ 脚本落盘到 `_xxx.txt`，再 Read 读结果。cmd 的 `mklink` 对中文路径报
  「系统找不到文件」→ 改用 PowerShell `New-Item -ItemType Junction`。

### ⑦ 代理会掉线
本轮中途 V2RAYN 被关，10808 端口无监听，curl 全部 000。
→ 下载脚本改成**自动探测**：有代理用 HF 官方源（4.9MB/s），无代理用 hf-mirror 直连（3.2MB/s）。
用户可以直接在 cmd 里 `set http_proxy=...` 解决。

## ⭐⭐⭐ 最重的一条：分片下载跨源拼接 = 内容错位（尺寸对、内容全坏）

**这是本轮最贵的教训，19.5GB 白下了两遍。**

**怎么坏的**：
1. 前 8.5 片用 hf-mirror 直连下的，续传超长后被 `head -c` 截断
2. 后 1.5 片换 HF 官方代理源续传
3. 两次下载的**字节流边界对不上**（源站返回的 Range 起点有偏差）
4. 拼起来 → 尺寸正好 20970379616，头部完整，**但数据区整体错位**

**为什么校验没拦住**（关键）：
`_verify_models.py` 验的是「尺寸 + 张量头尾自洽」，一份错位文件**照样通过**
—— 因为 safetensors 头是完整下载的，错位只发生在数据区。
→ **头尾自洽 ≠ 内容正确。**

**真正的探针**（`_check_quant.py`）：
H3 量化模型的 `comfy_quant` 张量存的是 **UTF-8 JSON 文本**（量化配置），
天然的内容探针：
```python
json.loads(该张量的字节)   # 坏文件会报 UnicodeDecodeError: 0xd5
```
ComfyUI 加载报的正是这个错：
`json.loads(layer_conf.numpy().tobytes())` → `UnicodeDecodeError: 0xd5 in position 0`

验证有效性：用老 turbo 模型跑同一个脚本 → 200 个全过；坏 DiT → 200 个全挂。

**铁律**：
1. **大文件下载全程单一源，不中途切源。**换源必须从头重下，不能续传拼接。
2. 分片下载后合并，**必须用内容探针验，不能只验尺寸**。
3. 判断文件完不完整，优先找「有语义的字段」当探针（如这里的 JSON 文本张量），
   不要只比对字节数—— 字节数对只说明没截断，不说明没错位。

### ⑩ `head -c` 截断后不重新 stat 会误报
脚本里 `got` 存的是截断**前**的值，截断后再拿它校验必然报「大小不符」。
→ 截断后必须重新 `stat`。

### ⑪ `dd bs=1048576 count=N` 只能整MB，最后余数用
`tail -c +$((N*1048576+1)) file | head -c R` 补。

## ⭐⭐⭐ 第二次翻车：`curl --retry` + `>>` 追加 = 内容重复拼接（脚本级bug）

`_dl_dit_fresh.sh` 跑到 100% 后文件涨到 **22.4GB**（超出目标 1.43GB），
我把它kill 掉并截断回精确 20970379616 字节 —— **结果 200/200 个 comfy_quant 全部读不出JSON**，
整份20GB 里搜不到一个 `int8_tensorwise` 标记。

**病根在第 26-27 行**：
```bash
curl ... --retry 30 --retry-all-errors --retry-delay 3 \
     -r $CUR-$((WANT-1)) "$URL" >> "$TMP"
```
`--retry` 在连接中断后**从本次 Range 的起点重新请求**，而 `>>` 又把这次重下的
**完整字节追加到文件末尾** → 同一段数据写了两遍 → 整份文件数据区错位。

**症状对照（下次见到直接认）**：
- 文件**涨过**目标尺寸 → 重试重复追加
- 头部声明 `comfy_quant` 是 `U8[72]`（72 字节 JSON 文本），实际却是权重字节
- `_verify_models.py`（尺寸+头尾自洽）**照样通过**
- `int8_tensorwise` 全文搜索命中 **0** 次

→ 已把该脚本改成事故记录（顶部加⛔ 禁止执行），另写 `_dl_dit_v3.sh`（无 --retry、
   全量单发、每次新建 part 文件）。
→ **但最终决定不让脚本下**：交给用户手动下，见 `_下载清单_H3原版DiT.md`。
