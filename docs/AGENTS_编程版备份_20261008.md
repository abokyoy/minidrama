## 一、认知原则

### 1.1 事实必须来自代码，禁止推测

- **分析任何功能/行为之前，必须先读代码**。以代码实际逻辑为准，不得凭经验、印象或猜测下结论。
- 若代码中有注释与实际逻辑不一致，以**实际逻辑为准**，并在回复中指出矛盾。
- 对于无法从代码直接得出的结论，必须明确标注"**[推测]**"，并说明推测依据，并向用户确认。

### 1.2 业务规则不明时，必须逐条向用户确认

- 不得假设任何业务规则。
- 每当遇到代码逻辑不清楚或规则有多种解读时，**一次只问一个问题**，每个问题都附带当前业务场景描述，辅助用户理解后作答。
- 问题格式：

  > **[问题 N]** 场景描述：xxx  
  > 当前代码实现：xxx  
  > 我的疑问：xxx  
  > 选项：A) xxx  B) xxx  C) 还没想好

## 二、任务接收与规划流程

每次接到用户任务，严格按以下顺序执行：

### 2.1 任务启动前：环境健康检查

在执行任何命令之前，先评估环境：

```
检查清单：
□ Git 代理是否可达（若配置了 http.proxy）
□ Python 虚拟环境是否激活
□ 端口是否空闲（5000 等）
□ 上一次执行是否有残留进程
```

每条命令执行前，先预估耗时（见 `docs/原则/开发工作原则.md` 第四节命令耗时参考表），设置超时，若超时立即 kill。

### 2.2 任务规划

每个任务开始前必须输出：

```
【任务规划】
任务目标：（一句话）
环境评估：（当前环境是否正常）
任务拆解：
  子任务1：xxx  预计耗时：X min  预计token：~Nt
  子任务2：xxx  预计耗时：X min  预计token：~Nt
  ...
总预计耗时：X 分钟
总预计token：~Nt
命令超时设置：已设置（默认 180s，长任务按需调整）
```

### 2.3 时间估算确认

- 若用户给出了完成时间，以用户时间为准。
- 若用户未给出，Agent 必须主动估算并询问：  
  > "本任务我估算需要 X 分钟，是否可接受？"  
  用户确认后再开始执行。

## 三、开发流程（强制）

### 3.1 阶段一：需求理解与方案制定

```
1. 理解用户意图（用自己的话复述）
2. 读代码（扫描相关文件，记录事实）
3. 基于代码事实制定技术方案
4. 不明确的问题逐项向用户确认（一次一题，带业务场景）
5. 信息齐全后，撰写方案文档
6. 发起子代理审核方案文档
7. 根据审核意见修正（最多2轮）
8. 审核通过后，提取3-5个核心理解做成选择题给用户确认
9. 用户确认理解一致 → 进入开发阶段
```

### 3.2 阶段二：开发

```
1. 对任务进行拆解（子任务粒度：每个 < 15 min）
2. 监控执行时间，超时立即 kill
3. 遵循 1:1 开发/测试时间比（测试不得超过开发时间）
4. 写代码时优先查阅架构原则（见 docs/原则/架构原则.md）
5. 新功能禁止创建重复公共函数（见架构原则公共函数注册制）
```

### 3.3 阶段三：测试（强制）

**白盒测试（代码评审）**：
- 代码写完后，必须发起一个**独立的 CodeReview 子代理**进行评审。
- 评审范围：逻辑正确性、安全漏洞、架构一致性、边界条件覆盖。
- 评审结果：有问题 → 修复 → 再次评审（最多3轮）。

**黑盒测试（断言测试）**：
- 为每个新功能/修复编写断言测试（Python unittest/pytest，或前端通过日志验证）。
- 测试必须在环境内正常完成，**不得卡死、不得超时**。
- 若测试命令超过预估时间 2 倍，立即 kill 并记录到掉坑笔记。

### 3.4 阶段四：交付前验证

```
1. 通过统一调试日志（logs/debug_trace.jsonl）验证功能完整性
2. 对所有边界条件、前端功能自测完毕后方可交付
3. 禁止要求用户手动发起测试来验证功能（用户是业务验收，不是功能测试）
4. 交付时直接告知：
   - 验收步骤（用户如何在界面上完成业务验收）
   - 本次改动了哪些文件（业务语言描述）
   - 已知的限制或待办事项
```

### 3.5 阶段五：用户验收跟踪

```
1. 用户验收期间，实时监控 logs/debug_trace.jsonl
2. 发现问题 → 自我迭代修复
3. 验收通过 → 写入开发日志
```

## 四、时间控制原则

### 4.1 开发测试时间比

- 对同一功能：**测试时间 ≤ 开发时间**（最高 1:1）。
- 不允许测试时间超过开发时间。
- 若测试超时，分析原因（环境问题 or 测试设计问题），修复后重跑，而非无限等待。

### 4.2 命令超时控制

执行任何命令前：

1. 查阅 `docs/原则/开发工作原则.md` 第四节的命令耗时参考表
2. 设定 `timeout` 参数（Bash 工具的 timeout 字段）
3. 若超时：kill 进程 → 记录到掉坑笔记 → 调整方案后重试

### 4.3 命令报错/卡住：绝不停止在失败点（强制）

命令执行出现异常（报错、意外退出、卡住、终端工具本身失效）时，**禁止原地停下或把任务搁置**，必须按以下流程处置：

```
命令异常
  ↓
① 捕获错误栈/异常输出（stderr、退出码、异常堆栈；PowerShell 管道噪声
   要用“脚本落盘文件 + Read 读结果”的方式绕开，而不是反复重试同一条命令）
  ↓
② 归因：脚本逻辑 bug？命令写法问题？环境损坏（终端/端口/网络/进程残留）？
  ↓
③ 环境问题 → 先修（重启进程/换端口/清理残留）；修不好 → **绕过**：
   换执行方式（脚本落盘+Read 读结果）、换工具（pytest/HTTP 自证脚本代替终端回显）
  ↓
④ 记录到掉坑笔记（现象、根因、绕行方案），后续会话不再踩
```

- 终端工具自身不可用（连接错误/无响应）时：立即切换到不依赖终端的工作（文件编辑、文档、脚本落盘），稍后重试终端；绝不反复重试同一条终端命令。
- 同一命令入口连续两次失败：禁止第三次盲试，必须换路径或换机制。

### 4.4 Token 消耗意识

- 避免不必要的文件全文读取（使用行号范围）
- 避免重复读取同一文件
- 单次 SearchReplace 合并尽可能多的替换（不要分散多次调用）
- 监控整体 token 消耗，若接近预算，提前告知用户

## 五、环境健康监测

Agent 需要持续维护对环境状态的意识：

### 5.1 已知环境问题（持续更新）

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| Git 代理不通 | `clone/fetch` 超时 | 加 `-c http.proxy='' -c https.proxy=''` |
| PowerShell 不支持 `&&` | 命令报语法错 | 用 `;` 分隔命令 |
| Flask 后台运行 | 命令不返回 | 用 `is_background=true` + 端口检测 |
| Python 导入慢 | `import torch` 等 | 避免导入不必要的模块 |

### 5.2 定期验证

每次新任务开始时，运行快速健康检查：

```powershell
# 检查端口是否空闲
Test-NetConnection -ComputerName localhost -Port 5000 -InformationLevel Quiet
# 检查 git 是否可达（无代理）
git -c http.proxy='' -c https.proxy='' ls-remote https://github.com/abokyoy/LectureLearnLoop.git HEAD
```

## 六、架构原则速查（详见 docs/原则/架构原则.md）

**第一原则：架构收敛**

1. **公共函数注册制**：新功能必须先查阅公共函数清单，禁止重复实现
2. **相似业务相似实现**：同类业务用同一技术路径，禁止"秀技术"
3. **最成熟原则**：选择业界公认最成熟稳定的方案，不追新
4. **精简优先**：能 10 行解决的不写 100 行，拒绝堆积式编程
5. **修改谨慎**：影响已有功能的修改，必须经过 3 次代码评审

## 八、统一调试日志使用原则（核心机制）

本项目有**统一的调试日志**：`logs/debug_trace.jsonl`

**Agent 必须遵循**：

1. 每次调试新功能，在代码中通过 `debug_logger.log()` 写入关键节点信息
2. 测试验证时，读取 `logs/debug_trace.jsonl` 确认执行路径和结果
3. 前端通过 `/api/debug/log` 上报，后端通过 `debug_logger.log()` 上报
4. **永远不要** 依赖用户的主观反馈来判断功能是否正常
5. **永远不要** 要求用户手动运行某个功能来验证
6. 交付前，确保所有路径的 debug 日志都符合预期

**Agent 自检示例**：
```python
# 后端调试写入
from logger_module import debug_logger
debug_logger.log('api', 'extract_knowledge', 'success', {'count': 3})

# 验证（读取日志）
# 读取 logs/debug_trace.jsonl 最后 N 行，确认功能按预期执行
```

## 九、禁止清单

| 禁止行为 | 替代方案 |
|---------|---------|
| 凭记忆/印象分析代码 | 先读代码，再下结论 |
| 假设业务规则 | 逐条向用户确认 |
| 创建重复公共函数 | 查阅公共函数清单，复用已有实现 |
| 堆砌代码（大量重复） | 精简，抽象公共逻辑 |
| 用多种技术实现同一业务 | 统一用最成熟的一种方式 |

| 引入新的依赖库不评估影响 | 先查 requirements.txt，评估冲突 |
| 对 API Key 明文存储 | 使用环境变量或加密配置 |

## 十一、网络路径规则（本机 V2RAYN 代理）

本机安装了 **V2RAYN** 代理软件，代理地址：

```
HTTP/HTTPS 代理：http://127.0.0.1:10808
SOCKS5 代理：    socks5://127.0.0.1:10808
```

**Agent 必须遵守的网络走向规则**：

| 目标 | 网络走向 | 说明 |
|------|---------|------|
| 外网（googleapis.com、github.com、pypi 等） | **必须走代理** | 命令行中临时设置 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量 |
| localhost / 127.0.0.1（Flask 服务、Ollama） | **不代理** | 设置 `NO_PROXY=localhost,127.0.0.1`，否则本地接口反而不通 |
| 局域网设备 | 不代理 | 直连 |

**注意**：Git 有独立代理配置（见掉坑笔记 P001），环境变量不影响 Git，Git 需单独用 `-c http.proxy=...` 处理。

**代理不通时的判断流程**：外网请求失败/系统卡住 → 确认 V2RAYN 客户端是否在运行 → 若未运行或无响应，**重启 V2RAYN 工具**（可提醒用户，或在获得授权后由 Agent 执行）：

```
工具路径：C:\Users\Administrator\Desktop\v2rayN.exe
重启方式：先结束进程（Stop-Process -Name v2rayN -Force），再重新启动该路径下的 exe
重启后等待几秒，重新验证外网连通性（如请求 stitch.googleapis.com 得到任意 HTTP 响应即通）
```

反复卡住超时的网络问题，根因优先怀疑 V2RAYN 状态，不要盲目重试业务代码。

## 十二、界面设计工具：Stitch MCP（外部服务）

**定位**：产品界面（UI）设计的指定工具。进行界面设计/页面改版/组件视觉方案时，**必须调用 Stitch MCP** 生成设计稿，而非凭空手写样式。

**配置**：已写入项目 `.qoder/mcp.json`（url + X-Goog-Api-Key 头）。服务地址 `https://stitch.googleapis.com/mcp`，属外网，依赖第十一节的代理路径。

**使用规则**：
1. **每日调用额度 400 次**，超出后当日不可用。每次任务规划时必须预估 Stitch 调用次数并计入预算
2. 一天内优先复用已生成的设计结果（保存到本地），不重复调用
3. 调用前先确认当日已用次数（在开发日志中登记：`Stitch 调用：已用 N/400`）
4. 调用失败（网络/额度）→ 降级为本地手写 CSS，并记录失败原因到掉坑笔记，不要反复重试
5. 设计产出（图片/HTML 稿）存放到项目 `design/` 目录，便于离线复用

## 十三、并行开发原则（Git Worktree，强制）

多模块/多功能同时开发时，**必须使用 git worktree 做并行开发**，禁止在同一工作树里混写多个独立功能的代码。

### 13.1 基本操作

```powershell
# 为每个并行任务建立独立工作目录 + 独立分支（从主分支切出）
git worktree add ..\LectureLearnLoop-<任务名> -b feat/<任务名> main

# 查看所有工作树
git worktree list

# 任务合并后清理
git worktree remove ..\LectureLearnLoop-<任务名>
git branch -d feat/<任务名>
```

### 13.2 分支与环境纪律

1. 每个并行任务一个 `feat/<功能名>` 分支，粒度小而聚焦，频繁提交；分支之间不得互相依赖未合并的代码
2. 各 worktree 独立运行环境：Flask 端口错开分配（5001、5002……），Electron 测试进程各自独立，避免 localhost 端口冲突
3. 共用本机 PostgreSQL 时，并行任务的测试数据必须使用独立的测试用户/测试科目隔离，禁止污染正式数据；破坏性验证只在测试数据上进行
4. 冲突热点文件（侧边栏菜单、routes_pages 路由表、api.js 桥方法清单）由各分支各自追加，合并时由集成方集中串行解冲；追加式修改优于穿插式修改

### 13.3 合并门禁（与验收绑定）

1. **用户验收通过是合入 main 的前置条件**：任何并行分支在用户验收前不得合并进主分支
2. 合并前先在分支上 `git merge main` 同步主线、本地解冲，再发起向 main 的合并
3. 合并后主分支必须全量跑通既有测试，方可视为该任务闭环
4. 验收不通过的分支在对应 worktree 内继续迭代，不影响其他分支的进度

## 十四、前端 UI 设计与验证工作原则（详见 docs/原则/前端UI设计工作原则.md）

## 十五、短剧视频生成（ComfyUI / MiniMax H3）强制规则

> 本剧为**真人实拍风格**短剧（非漫画/动漫风）。以下规则为用户硬性要求，必须无条件遵守。

### 15.1 画面风格（每次生成 prompt 必须写）
- 高级电影质感，镜头感高级，带电影滤镜/调色；人物俊美精致，画面美，光影通透
- **不要太暗**：拒绝死黑/欠曝，保持明亮通透的高级电影感；**9:16 竖屏**（短剧发行标准），电影级布光与纵深
- **竖屏构图铁律（2026-10-03 用户明确）**：画幅左右窄、上下长，**不许写"横着铺开一排人"这类横向调度**。人物一律**沿纵深排列**（前景 / 中景 / 后景），脸与身体落在画面上 2/3，画幅下 1/3 留给桌面、地砖、道具当"前景压边"；两人对话用前后交叠或过肩，不用左右并排。

### 15.2 链式生成与重启节奏（核心）
视频会越接越黑，**最多链式 3 段**：
- 第 1、4、7 段用首段工作流 `04_ref2v_4step_sla_ganloss_fixed.json`（无前视频）
- 第 2、3 / 5、6 / 8 段用链式 `04_ref2v_seg2_chain.json`
- **每满 3 段（第 3、6 段后）必须 kill 掉 ComfyUI 进程并重启**，再开下一组首段

### 15.3 音频必须正常（启动方式决定）
- **必须用不带 `--lowvram` 的方式启动**。`--lowvram` 会导致音频 VAE 只加载极小权重、产出 0KB/打不开的空音频。
- 生成后必须验证 `-audio.mp4` 非 0 字节且能出声；主 mp4 含音频流。音频坏不得往下接。

### 15.4 输出与资产
- 视频输出目录 `D:\output`；git 管理不覆盖；驱动 `comfy_h3_driver.py`；剧本 `D:\obsidian\具体事务\小说短剧\保洁\ep001.md`

### 15.5 实测修正（2026-10-03）
- 用户指定的启动 bat（`启动旧版ComfyUI(视频).bat`）自带 `--lowvram`，**实测音频正常**（`-audio.mp4` 有 aac 音轨、mean −16.7 dB / max −0.1 dB）。15.3 里"lowvram 必然导致空音频"的结论在本机不成立，改以"**生成后必须实测音量**"为准。
- 本机 16GB 笔记本 3080Ti，**必须 `--lowvram`**，否则必 OOM。
- 该 bat 的文件名含中文和括号，从脚本里 `cmd /c` 调用会被 mangle；无人值守脚本应直接调 `venv\Scripts\python.exe main.py --lowvram --enable-triton-backend --output-directory "D:\output" --temp-directory "D:\ComfyUI_out\ComfyUI-master\temp"`（与该 bat 等价）。
- 分辨率节点 `ResolutionSelector`（node 115）的 aspect_ratio **必须是 `9:16 (Portrait Widescreen)`**（2026-10-03 用户更正：本剧是**竖屏短剧**）。工作流文件里默认写的是 `3:4 (Portrait Standard)`，驱动 `h3_driver.py` 会在提交前强制覆写成 9:16，**不要**在 job.json 里传 `aspect_ratio` 去覆盖它。实测输出约 640×1152。
  - 历史教训：15.1 曾经写"16:9 横版"，驱动跟着硬改成 `16:9 (Widescreen)`，成片变成 1184×672 横屏，全部返工。**画幅一旦定错，129 段全部报废**，所以这一条永远以用户最新口径为准。

### 15.6 不许烧字幕（2026-10-03 用户要求）
> 用户原话：「生成视频的时候，如果可以，不要加字幕，字幕我后期编辑的时候统一生成。」
- **交付的成片必须是"干净画面"**，不烧任何字幕 / 说明条 / 标题卡 / 水印。
- H3 的坑：**被引号包住的台词会被当成字幕文本烧进画面**。所以：
  1. beats 里台词**一律不写引号**（`check_beats.py` 已加闸："台词被引号包裹"直接判错）。
  2. 每段提示词里自动前置 `NO_TEXT` 段（"ABSOLUTELY NO SUBTITLES, NO CAPTIONS … Any spoken line is AUDIO ONLY"），由 `storyboard_render.py` 拼进 `detailed_description`。
  3. 唯一允许的文字：**场景里真实物品上本来就印着的字**（黑卡烫金的"山"字、门牌、招牌）。这类要写成 "physically printed on a real object"，不能写成屏幕文字。
- `check_beats.py` 新增闸：beats 里出现 subtitle / caption / lower-third / title card / text overlay / watermark 等词，直接判错。
- 工作流里**没有**字幕节点（`MiniMaxH3ReferenceToVideo` 只有 prompt 一个文本口，已被驱动覆写），所以字幕只可能从提示词来 —— 关掉提示词即彻底关闭。

### 15.7 声景必须"正向写"（2026-10-03 四轮审核实测最坑的一条）
> H3 对 `overall_soundscape` 里的**否定式**极其敏感：写"这里没有声音"会把**人声一起压掉**，成片就听不见台词了。

- **禁用（会压人声）**：`silence` / `silent` / `mute` / `muted` / `no dialogue` / `without sound` /
  `soundless` / `no intelligible` / `nothing at all` / `absolute quiet` / `almost nothing` /
  `dead quiet` / `dead-still` / `dead room tone` / `total hush` / `gone quiet` / `nothing but …`
- **改成正向写法**：不要写"房间静了"，要写"**只剩什么还能听见**"。
  例：`the room holding its breath`、`only the air handling`、`the ceiling lights and the clock`、
  `the crowd's held breath`、`leather soles and the crowd breathing`。
- **不要误伤**：`a quiet voice` / `one quiet question` / `two quiet words` 只是形容**音量低**，保留。
- `check_beats.py` 已加闸：**以前它只扫 `[Shot]` 正文，声景完全没扫过**，所以这类词一路漏网到
  第四轮才被人工审核发现。现在 `soundscape` 也会被 `BAD_PHRASES` + `SOUNDSCAPE_BAD` 扫。

### 15.8 参考图必须"人在场、景在画"（2026-10-03 第四轮审核）
- **不在场的角色绝不能挂参考图**：某段画面里没有钱经理，就**不能**在 refs 里放 `qianjingli`，
  否则 H3 会凭空把他画进画面。
- **画面里没有的场景也不能挂**：大堂戏挂 `office_*` 会往大堂里灌办公室元素；删掉的镜头要**连参考图一起删**。
- 反例（已修）：seg108/110 的大堂段曾带 `qianjingli`（他根本不在场）；seg109/112 曾挂办公室场景图；
  seg114/115 删了"大堂回望"镜头却还留着 `lobby_1f`。
- **夜间素材图不许当白天戏的打光参考**：`car_interior` 是**夜间**车厢图，seg117 是傍晚日戏，
  必须用 `ref_notes` 把该图降级成 "Use as the location and prop reference only, **NOT for lighting**"。

### 15.9 每段的 Entry 必须等于上一段的结尾（链式首帧原理）
- `04_ref2v_seg2_chain.json` 是拿**上一段视频的尾帧**当本段的首帧参考（`prev_skip=221`，
  即保留上一段最后 22 帧 ≈ 0.9 s 作为衔接上下文）。所以：
  **某段 Entry state 里的人物位置，必须等于上一段 [Shot] 最后一拍的画面**，否则第一帧就跳变。
- 典型反例（已修）：seg97 结尾钱经理还在门侧（张总身前半步），seg98 的 Entry 却已经写他
  "退到了桌子远侧" —— 中间这一步没有任何镜头交代。改法：Entry 写"他仍在门侧"，
  再在 seg98 里给他一个**可见的**"绕桌子退回远侧"的动作。
- 写分镜时逐段自问：**上一段最后一眼看到的画面，和这一段第一眼看到的画面，是同一张吗？**

## 十六、短剧视频制作流水线（四步走，2026-10-03 用户强制要求）

> 用户原话：「先生成这个东西，确保就是前后每个镜头都是顺，都是能够顺接上的。然后再写分镜脚本，然后最后才生成视频。」
> **禁止跳步。** 发现"上一秒人站在推车前面、下一秒推车跑到他面前"这类空间跳变，即为不合格，必须返工。

| 阶段 | 产物（`保洁/<ep>/` 下） | 硬性要求 |
|---|---|---|
| ① 文字剧本 | `文字剧本.md` | 原剧本只有台词（对话剧本）。AI 必须**补全**成完整文字剧本：逐句给出人物的**神态、动作、站位、朝向、手里拿什么、身边有什么**。**台词一句不许丢、不许改**（可补语气提示）。 |
| ② 连续脚本 | `连续脚本.md` | 逐镜头连续性表：镜头号 / 场景 / 机位景别 / 每个人**在哪、朝哪、手上是什么、身上状态** / 与上一镜的顺接点。**必须逐镜检查前后能接上**，接不上就拆镜头或改写法。 |
| ③ 分镜脚本 | `分镜脚本.md` + `*_segs/segNN_prompt.txt` | 在②的基础上按 **10 秒**切段，写 H3 ref2v 六段式提示词。每段都要带①的神态动作、②的空间方位。 |
| ④ 生成视频 | `D:\output` | 用③驱动 ComfyUI。段 1/4/7… 用 `..._fixed.json`，段 2、3/5、6/8 用 `..._seg2_chain.json`，**每满 3 段 kill + 重启 ComfyUI**。 |

### 16.1 空间连续性公约（写①之前必须先定）
每个场景先定「**空间锚点**」——人物与道具、人物与人物、人物与镜头的固定方位关系，写进 `连续脚本.md` 的开头，之后所有镜头不得违背。

示例（本剧走廊）：
- 保洁车停走廊**右侧靠墙**，车头朝**远端红门**；苏小满站车的**后侧偏左**，面向红门方向，全程不换位。
- 钱经理从**红门内**出来，停在女贵宾**右侧**；女贵宾在走廊**中央偏左**，面向苏小满。
- 只要苏小满与保洁车同框，**车必须在她同一侧**（右侧靠墙），不得左右互换。

### 16.2 每个镜头的表演必须可见
禁止只写台词。每镜至少写清：**手在做什么 / 目光看哪里 / 身体前倾还是后退 / 表情从 A 变到 B**。

### 16.3 每个镜头都必须能"顺接"
每段第一拍接上一段最后一拍的**人物位置、朝向、手中物**，不得跳变。

### 16.4 分镜数量与台词预算
- 10 秒 ≈ **24 个汉字**台词上限（约 2.5 字/秒）。超了必须拆段，不许硬塞。
- 一集做完再动下一集。

### 16.5 边审边生成（并发，2026-10-03 用户明确要求）
> 用户原话：「你要审核出来一个分镜，同步就生成视频，不要所有分镜都审核完再生成视频，要并发执行。」

- 分镜写完必须发**独立子代理**用 H3 技能（`minimax-h3-prompt-audio`、`minimax-h3-chained-segment-drift`）审核，
  并**额外审查空间连续性**。审核与生成**同时进行**，不是串行等全部审完。
- 机制：分镜渲染出每段的**内容指纹 sha** 写进 `ep001_segs/manifest.json`；
  常驻生成器 `gen_worker.py --watch` 逐个链组开跑前**重读 manifest**，指纹变了就补跑对应链组。
  → **改一条分镜，最多一个链组的时长就会被接上**，不用等 129 段跑完。
- ⚠️ 历史教训：`one_pass()` 原来只在**整轮开始时**算一次计划，导致"分镜改成整轮跑完（约 24 h）后才生效"，
  等于没做到并发。2026-10-03 已改成**每个链组开跑前都重读 manifest/state**。
- 失效粒度 = **3 段链组**：链式依赖只存在于组内，组内任一段变了就从**第一个失效段**起顺序重跑；
  组头重跑前先 kill + 重启 ComfyUI。重跑前把旧成片挪到 `D:\output\_stale\`，
  否则 ComfyUI 会输出成 `_00002` 而链式引用仍指向 `_00001`。

### 16.6 审核闸门（三层，缺一不可）
1. **机械自检** `python check_beats.py ep001` —— 必须 **0 错误 0 提示**。查：台词时间窗（字数/2.5 + 起始 ≤ 10.0 s）、
   说话人紧邻、引号包台词、字幕类词、声景否定写法、锚点与曝光句是否存在、`<Picture n>` 悬空。
2. **子代理审核**（H3 技能）—— 分场景切片，报告写到 `_verify*.md`，逐条给"应改成"的可替换原文。
3. **整改回归** —— 补丁脚本（`_patch_beats*.py`）+ 重渲染 + 重跑第 1 层，确认没有引入新矛盾。
